Start in `ch17/build`. There are three recipe files, but two implementations:
`greeting-simple` versions 1.0 and 2.0, and `greeting-fancy` version 1.0.
All inherit [tutorial-greeting](../ch17/meta-tutorial/classes/tutorial-greeting.bbclass)
which declares `PROVIDES += "virtual/greeting"`.

## A target can be an alias

```bash
bitbake -s
bitbake virtual/greeting
cat tmp/work/greeting-simple-1.0-r0/selection.txt
bitbake -e virtual/greeting | grep -E '^(PN|PV|PROVIDES)='
bitbake -g virtual/greeting
```

Expect `simple 1.0`, with `PN="greeting-simple"` and `PV="1.0"`.
`PROVIDES` adds alternative build-time names to a recipe's implicit `PN`.
The `virtual/` prefix is a naming convention, not an extra recipe or task.
The chosen recipe still runs its own `do_build`.

The same alias can be used in `DEPENDS` (with a `[deptask]` policy) or in
`do_something[depends] = "virtual/greeting:do_build"`. A virtual name does not
automatically define a common artifact path; providers must agree on an
output contract if another recipe will consume their files.

## Choose implementation, then version

The snapshot's `local.conf` sets:

```bitbake
PREFERRED_PROVIDER_virtual/greeting ?= "greeting-simple"
PREFERRED_VERSION_greeting-simple ?= "1.0"
```

These variable names retain underscores: they are documented variable-name
suffixes, **not legacy override syntax** to convert to colons.
Provider selection picks the recipe name; version selection is keyed by
that recipe name, not by `virtual/greeting`.

```bash
config=$(mktemp --suffix=.conf)
printf 'PREFERRED_VERSION_greeting-simple = "2.0"\n' > "$config"
bitbake -R "$config" virtual/greeting
cat tmp/work/greeting-simple-2.0-r0/selection.txt
printf 'PREFERRED_PROVIDER_virtual/greeting = "greeting-fancy"\n' > "$config"
bitbake -R "$config" virtual/greeting
cat tmp/work/greeting-fancy-1.0-r0/selection.txt
rm "$config"
```

Expect `simple 2.0`, then `fancy 1.0`. Version 2.0 has
`DEFAULT_PREFERENCE = "-1"` to mark it non-default/experimental; an explicit
`PREFERRED_VERSION` still selects it. `%` at the end of a preferred version
can match a version prefix, but exact versions make these exercises clearer.

`PREFERRED_VERSION` is a preference: an unavailable version can produce a
warning and fallback. `REQUIRED_VERSION` requests failure instead if that
version is unavailable. Layer priority is another selection input; Chapter 20
demonstrates it. Do not assume “highest version always wins.”

## Ambiguity and missing providers

```bash
config=$(mktemp --suffix=.conf)
printf 'PREFERRED_PROVIDER_virtual/greeting = ""\n' > "$config"
bitbake -R "$config" -g virtual/greeting
rm "$config"
bitbake virtual/no-such-greeting
```

Without the preference, BitBake 2.18 reports multiple providers and suggests
setting `PREFERRED_PROVIDER`. It can still choose an eligible provider;
ambiguity is not necessarily a fatal error. Do not rely on the incidental
choice. Restore the preference before continuing.

The final command intentionally fails with
`Nothing PROVIDES 'virtual/no-such-greeting'`. No matching recipe or alias
exists. Inspect `BBFILES`, masking and layer configuration before assuming a
task-order problem. A missing task on an existing provider is a different
error.

`RPROVIDES:${PN}` supplies runtime aliases for `RDEPENDS`, not build aliases;
`PREFERRED_RPROVIDER` can select among them. As Chapter 15 explains, package
names in metadata do not cause this standalone project to emit packages.
Likewise `native` and `nativesdk` are OE-Core class policies, not magical
suffixes. Chapter 20 creates a small custom recipe variant instead.

Run `bash tests/check-ch17.sh` from the repository root for all three
selections, the ambiguity diagnostic, and the missing-provider failure.
