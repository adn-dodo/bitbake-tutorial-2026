## Define an output contract, not a guessed work path

[artifact-source](../ch15/meta-tutorial/recipes-advanced/artifact-source/artifact-source_1.0.bb)
publishes `payload.txt` under `${TUTORIAL_ARTIFACTS}/artifact-source`.
The common config defines `TUTORIAL_ARTIFACTS = "${TMPDIR}/artifacts"`.
Consumers do not guess the producer's `WORKDIR`, version or revision.

`do_runtime` copies that payload to `runtime.txt` after `do_publish`.
Neither task deletes a directory shared with other producers. In a larger
project, output ownership and atomic publication need deliberate policy.
This tutorial has one writer per file and readers ordered after that writer.

## Three ways to create a real task edge

Read [artifact-user](../ch15/meta-tutorial/recipes-advanced/artifact-user/artifact-user_1.0.bb).

| Consumer flag | Recipe metadata consulted | Required producer task |
|---|---|---|
| `do_explicit[depends] = "artifact-source:do_publish"` | Direct recipe/task pair | `do_publish` |
| `do_via_depends[deptask] = "do_publish"` | `DEPENDS = "artifact-source"` | `do_publish` |
| `do_via_runtime[rdeptask] = "do_runtime"` | `RDEPENDS:${PN} = "artifact-source"` | `do_runtime` |

DOT edges point from the consumer task to its prerequisite. All three
consumer tasks precede their own `do_build`; they may otherwise run in
parallel. The producer's publish task runs only once in the graph.

The runtime example defines `PACKAGES = "${PN}"` in both recipes so BitBake
has names on which to resolve runtime dependency metadata. **This does not
create packages.** We deliberately provide the `do_runtime` task ourselves.
There is no `do_package`, package splitting, package manager or installed
runtime environment in this project.

`DEPENDS` refers to recipe/build providers; `RDEPENDS` refers to runtime
providers. A class often applies `[deptask]` or `[rdeptask]` globally, which
is why these declarations can seem magical in a full Yocto build.
Without task policy and resolvable providers, declarations alone do not
produce the expected files.

For completeness, `[rdepends]` names explicit runtime-provider/task pairs,
whereas `[recrdeptask]` requests tasks through the recursive build/runtime
dependency closure. Recursive policies can greatly expand a graph; use them
only when that full closure is intended, rather than adding dependencies to
hide a missing direct edge.

## Dependencies also carry signatures

```bash
config=$(mktemp --suffix=.conf)
printf 'ARTIFACT_MESSAGE = "Shared artifact v2"\n' > "$config"
bitbake -R "$config" artifact-user
cat tmp/work/artifact-user-1.0-r0/{explicit,deptask,rdeptask}.txt
rm "$config"
bitbake artifact-user
```

All three outputs first change to `v2`, then return to `v1`. The producer's
metadata is in its signature, and prerequisite task hashes feed the consumer
signatures. No manual force is required.

BitBake does not generally monitor arbitrary output files. If somebody
deletes a published file while its stamp remains valid, a consumer may fail
or a stamped consumer may be skipped. `bitbake -C publish artifact-source`
recreates the producer outputs; then build the consumer again. A dependency
edge is an ordering and signature contract, not an automatic file-transfer
or output-existence service.

From the repository root, `bash tests/check-ch15.sh` checks all graph edges
and exact output contents before and after the metadata change.
