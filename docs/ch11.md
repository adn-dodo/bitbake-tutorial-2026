## Ordering is a dependency, not a numbered script

Read [task-order](../ch11/meta-tutorial/recipes-advanced/task-order/task-order_1.0.bb)
and [task-source](../ch11/meta-tutorial/recipes-advanced/task-source/task-source_1.0.bb).
Their execution constraints are:

```text
task-order:do_begin ------------------+
                                     v
task-source:do_prepare -> task-order:do_middle -> do_finish -> do_build
```

`do_begin` and `task-source:do_prepare` can run in parallel. There is no total
ordering between unrelated nodes, even with a small worker count.
In the DOT file an arrow points from a task to its **prerequisite**, opposite
to the execution-flow arrows drawn above.

`addtask middle before do_finish` registers a task and adds an edge.
Equivalently, the finish declaration could say
`addtask finish after do_middle before do_build`. The `do_` prefix may be
omitted for the task being added; use full task names in dependency flags.
Merely defining a function does not make it a scheduled task.

```bash
bitbake -c middle task-order
```

This requests middle and its predecessors, not finish or build. Stamped
predecessors may already be current. `-f -c middle` forces middle, but does
not automatically request its successors; `-C middle task-order` invalidates
middle and requests the default build graph. `-n` shows a dry run.

The middle and finish tasks append to `order.txt`; only begin resets it.
Forcing middle therefore adds lines without rerunning a current begin task.
After experimenting, reset the trace by rebuilding from begin:

```bash
bitbake -C begin task-order
cat tmp/work/task-order-1.0-r0/order.txt
```

This produces exactly `begin`, `middle`, `finish` again. The forced-run
taint warning is expected; it does not mean the build failed.

### Why the forced-run warning persists

`-f` and `-C` leave a **taint marker**: BitBake records that a task was forced
rather than selected only by its normal inputs. The marker changes its
signature and can also invalidate dependent tasks. Subsequent builds can
still warn `is tainted from a forced run`, even when all tasks succeed.
The warning is not a request to force the task again.

For this chapter, the marker for middle is
`tmp/stamps/task-order-1.0-r0.do_middle.taint`; the reset command above also
creates `tmp/stamps/task-order-1.0-r0.do_begin.taint`. It is fine to leave them
while experimenting. If you want to remove these two warnings afterwards,
first restore any experimental metadata changes and complete the trace reset
above. With no build running, remove only those known exercise markers:

```bash
rm -f tmp/stamps/task-order-1.0-r0.do_middle.taint \
      tmp/stamps/task-order-1.0-r0.do_begin.taint
bitbake task-order
```

Removing markers changes hashes again; tasks may rerun. It does **not** clean
or restore task outputs and is not a repair for a failed build or an edited
source tree. Do not delete all stamps to silence a warning. For the patch
exercise in Chapter 13, use its documented fresh-source recovery instead.
[Chapter 16](ch16.md) explains the signature mechanism in more detail.

## Recipe declarations versus task edges

The recipe deliberately has both:

```bitbake
DEPENDS = "task-source"
DIRECT_DEPENDS ?= "task-source:do_prepare"
do_middle[depends] = "${DIRECT_DEPENDS}"
```

Only the task flag wires this standalone example. `DEPENDS` declares
recipe dependencies, but a task needs a `[deptask]` policy to turn those into
task edges. No such policy is installed here yet. Chapter 15 supplies one.
`[depends]` names explicit `recipe:task` pairs and does not require `DEPENDS`.

To demonstrate the distinction without editing the recipe:

```bash
config=$(mktemp --suffix=.conf)
printf 'DIRECT_DEPENDS = ""\n' > "$config"
bitbake -R "$config" -g task-order
grep 'task-source.do_prepare' task-depends.dot
rm "$config"
bitbake -g task-order
```

The `grep` should find nothing (exit status 1). `DEPENDS` remains present
in `bitbake -e task-order`, but there is no edge to source's prepare task.
`-R` reads extra configuration after the normal configuration, but before
recipes. The recipe uses `?=` for this knob so the extra configuration wins.

`deltask` removes a task without reconnecting its neighbors. If the goal is
to keep ordering while doing no work, `[noexec] = "1"` retains the node.
Do not introduce cycles: BitBake diagnoses a circular task dependency rather
than guessing an order. Chapter 18 covers explicit failure diagnostics.

From the repository root, `bash tests/check-ch11.sh` verifies both the
positive graph and the absence of the edge when `[depends]` is cleared.
It rebuilds from begin before checking the trace, so it also works after
the force/invalidate exercises without changing the recipes' stamp behavior.
