The complete new recipe is small enough to read before running it:

```bitbake
SUMMARY = "Assignment timing, overrides and task directory flags"

LATE = "one"
LAZY = "${LATE}"
EARLY := "${LATE}"
LATE = "two"
WEAK ??= "fallback"
WEAK ?= "default"
WORDS = "alpha beta"
WORDS:append = " gamma"
WORDS:prepend = "zero "
WORDS:remove = "beta"
OVERRIDES .= ":demo"
MESSAGE = "base"
MESSAGE:demo = "override"
LABEL = "recipe"
LABEL:task-report = "task"

python () {
    d.setVar("PARSED", "anonymous:" + d.getVar("MESSAGE"))
}

do_report () {
    printf '%s\n' "lazy=${LAZY}" "early=${EARLY}" "weak=${WEAK}" \
        "message=${MESSAGE}" "parsed=${PARSED}" "label=${LABEL}" > result.txt
    printf 'words=' >> result.txt
    echo ${WORDS} >> result.txt
    echo run >> runs.txt
    echo fresh > "${WORKDIR}/scratch/fresh.txt"
}
do_report[nostamp] = "1"
do_report[cleandirs] = "${WORKDIR}/scratch"
do_report[dirs] = "${WORKDIR}/preserved"
addtask report before do_build
```

## Work through the recipe in three passes

Do not try to memorize every operator from the full recipe at once:

1. Predict variable values, then inspect them without running a task.
2. Compare recipe and task contexts; follow how `MESSAGE`, `PARSED`, and `LABEL` are chosen.
3. Run the report twice to observe directory cleanup and repeated execution.

The signature policy is already configured for later chapters. You do not
need to understand its hashing details to complete these three passes.

## Pass 1: assignment is not always expansion

Read [operators_1.0.bb](../ch10/meta-tutorial/recipes-advanced/operators/operators_1.0.bb).
`=` defers expansion: `LAZY` sees the final `LATE`, `two`. `:=` expands
immediately: `EARLY` retains `one`. `?=` assigns only if the variable is not
already set, at parse time; the first effective `?=` wins. `??=` supplies a weak
default, replaced by another weak default or an ordinary assignment. Thus
`WEAK` is `default`, not `fallback`.

`+=` and `=+` append/prepend immediately with a separating space; `.=` and `=.`
do so without adding a space. Override-style `:append` and `:prepend` defer
their operation until expansion and add **no** space automatically. `:remove`
removes matching whitespace-separated items. These operations are applied in
append, prepend, remove order, regardless of their textual order.

```bash
bitbake -e operators > operators.env
grep -E '^(LAZY|EARLY|WEAK|WORDS)=' operators.env
```

Before continuing, explain why `LAZY="two"` but `EARLY="one"`, and why
`WEAK="default"`. `WORDS` retains the items `zero`, `alpha`, and `gamma`:
`beta` was removed. No build task has run yet.

`WORDS` in `-e` may retain extra whitespace; the report's shell `echo` will
normalize it. Inspect the variable's preceding comments in `operators.env`
to see its assignment history. Keep this dump for the next pass.

## Pass 2: overrides and datastore contexts

`OVERRIDES` is a colon-separated list of active conditions. Appending `:demo`
selects `MESSAGE:demo` over `MESSAGE`. Override names use lowercase letters,
digits and dashes, not colons or underscores. The rightmost active override
has priority when alternatives compete. Overrides are not shell environment
variables and `:append` is an operator, not an override called `append`.

The anonymous Python function runs during recipe finalization, not as a task.
It uses the recipe datastore `d` and creates `PARSED` with `getVar`/`setVar`.
Keep parse-time logic deterministic: no wall-clock time, downloads, or build
output generation. `${@...}` is an inline Python expression expanded as part
of a variable; anonymous Python is instead a metadata transformation.

BitBake adds `task-report` to the task-local overrides for `do_report`, so the
result says `label=task`, even though recipe-level `bitbake -e` says
`LABEL="recipe"`. Recipe and task datastores are distinct.

Inspect the recipe context first:

```bash
grep -E '^(MESSAGE|PARSED|LABEL|OVERRIDES)=' operators.env
```

Expect `MESSAGE="override"`, `PARSED="anonymous:override"`, and
`LABEL="recipe"`. Predict which of those will differ in the report. The
anonymous Python function only sets a variable during parsing; `do_report`
is the task that will write the output file.

## Pass 3: flags belong to variables and tasks

Flags use brackets, as in `do_report[nostamp]`. The report is ordered before
the inherited default `do_build`:

```text
do_report -> do_build
```

`[dirs]` creates directories and makes the last one the task working directory.
`[cleandirs]` removes and recreates its directories **when the task runs**.
`[nostamp] = "1"` means the task always executes when requested through this
graph. It does not mean all BitBake tasks always run.

Now run the task graph and compare its output with your predictions:

```bash
bitbake operators
cat tmp/work/operators-1.0-r0/preserved/result.txt
```

The result is:

```text
lazy=two
early=one
weak=default
message=override
parsed=anonymous:override
label=task
words=zero alpha gamma
```

Only `LABEL` changed between recipe inspection and task execution. Next,
predict whether scratch data and the run counter survive a second build:

```bash
touch tmp/work/operators-1.0-r0/scratch/stale
bitbake operators
test ! -e tmp/work/operators-1.0-r0/scratch/stale
cat tmp/work/operators-1.0-r0/preserved/runs.txt
cat tmp/work/operators-1.0-r0/temp/log.do_report
```

Each invocation adds a `run` to the preserved file, while the scratch
directory loses its old contents. Cleaning happens before the task body,
not during parsing or when a stamped task is skipped.

When all three passes make sense, remove the inspection file:

```bash
rm operators.env
```
