## What changed since Chapter 15

Added [signature-demo](../ch16/meta-tutorial/recipes-advanced/signature-demo),
including `files/input.txt`. It reuses `tutorial-fetch`; configuration and
classes are unchanged. The signature policy needed here has already been
loaded by `conf/bitbake.conf` since Chapter 10.

A task can be **current** without running. A stamp records successful
execution under a signature; it is not the task output. This chapter uses
BitBake's `basichash` handler, selected explicitly since Chapter 10.
The copied minimal configuration by itself would use the `noop` handler.

## Measure a task, not the whole build

From `ch16/build`:

```bash
bitbake signature-demo
cat tmp/work/signature-demo-1.0-r0/result.txt
wc -l tmp/work/signature-demo-1.0-r0/measure-runs.txt
bitbake signature-demo
wc -l tmp/work/signature-demo-1.0-r0/measure-runs.txt
find tmp/stamps -name 'signature-demo*'
```

Expect `first:alpha`. The run count is unchanged on the second invocation.
The inherited `do_build` still runs because the base class marks **that task**
`[nostamp]`. It does not force its stamped predecessors to rerun.
`signature-demo` has:

```text
do_fetch -> do_unpack -> do_measure -> do_build
```

The count file is an observation aid, not an input or an output manifest.
Its count can grow over multiple experiments; compare changes, not an
assumption that it always starts at one.

## The signature policy already in use

Chapter 10 loaded `conf/tutorial-settings.inc` from `conf/bitbake.conf`.
We postponed its details until we could observe task reuse. Its relevant
assignments are:

```bitbake
BB_SIGNATURE_HANDLER = "basichash"
BB_BASEHASH_IGNORE_VARS = "TOPDIR TMPDIR FILE"
BB_NUMBER_THREADS = "2"
```

`BB_SIGNATURE_HANDLER` selects how BitBake calculates task signatures and
uses them for stamps. Bare BitBake's default `noop` handler does not give
these examples the input-sensitive invalidation we need. `basichash` was
enabled before the source and build exercises so their metadata changes
could already trigger rebuilds; do not remove it from those snapshots.

`BB_BASEHASH_IGNORE_VARS` excludes the named project-location variables from
base hashes. Here they locate files rather than select semantic inputs.
This is a limited tutorial policy, not a recommendation to ignore arbitrary
variables; excluding a real input can reuse stale output.

`BB_NUMBER_THREADS` allows two task worker slots. It limits parallel
execution, not which tasks are dependencies or whether their stamps are
current. None of these assignments adds a shared-state cache, and the
inherited `do_build[nostamp]` remains unchanged.

## Base hashes, task hashes and input files

A task's base hash describes its code and relevant metadata. Its task hash
also includes prerequisite task hashes and declared file checksums.
`basichash` puts the task hash into the stamp filename. The dependency
changes from Chapter 15 thus invalidate consumers without forcing them.

[signature-demo](../ch16/meta-tutorial/recipes-advanced/signature-demo/signature-demo_1.0.bb)
looks up a variable by a dynamically computed name:

```bitbake
SIGNATURE_KEY = "SIGNATURE_MESSAGE"
do_measure[vardeps] += "${SIGNATURE_KEY}"
do_measure[vardepsexclude] = "DISPLAY_NOTE"
```

Static analysis cannot always infer indirect Python lookups. `[vardeps]`
declares the missing semantic dependency. `[vardepsexclude]` is appropriate
here only because `DISPLAY_NOTE` changes diagnostic text, not `result.txt`.
Ignoring a variable that affects output would permit stale results.

Try changing `SIGNATURE_MESSAGE` through an extra configuration:

```bash
config=$(mktemp --suffix=.conf)
printf 'SIGNATURE_MESSAGE = "second"\n' > "$config"
bitbake -R "$config" signature-demo
cat tmp/work/signature-demo-1.0-r0/result.txt
rm "$config"
bitbake signature-demo
```

The output changes to `second:alpha`, then returns to `first:alpha`.
Editing the checked-in `files/input.txt` to `beta` changes the fetch task's
declared file checksum. Fetch, unpack and measure rerun, yielding `first:beta`;
the unstamped build task also runs as usual.
Restore the file and build again. The automated check uses a temporary input
instead of modifying the checked-in file.

## Explain a signature difference

`-S none` dumps signature data without executing the build tasks. Earlier
experiments can leave several signature files. Capture the newest measure
signature immediately after each dump, rather than choosing an arbitrary
file from the directory. Do not run another build in this directory during
the comparison.

```bash
bitbake -S none signature-demo
before=$(find tmp/stamps -name 'signature-demo-1.0-r0.do_measure.sigdata.*' \
    -printf '%T@ %p\n' | sort -nr | sed -n '1s/^[^ ]* //p')

config=$(mktemp --suffix=.conf)
printf 'SIGNATURE_MESSAGE = "second"\n' > "$config"
bitbake -R "$config" -S none signature-demo
after=$(find tmp/stamps -name 'signature-demo-1.0-r0.do_measure.sigdata.*' \
    -printf '%T@ %p\n' | sort -nr | sed -n '1s/^[^ ]* //p')

bitbake-diffsigs "$before" "$after"
bitbake-dumpsig "$after"
rm "$config"
```

The difference names `SIGNATURE_MESSAGE` changing from `first` to `second`.
`bitbake-dumpsig` displays the second signature's dependencies. These commands
do not change `result.txt` or the measure run count; the temporary configuration
applies only to the second signature dump.

Do not use `bitbake -S printdiff signature-demo` in this standalone setup.
Unlike file-to-file `bitbake-diffsigs`, it requires a metadata signature lookup
implementation (`find_siginfo`), normally supplied by OE-Core. Our `basichash`
configuration does not provide it, and BitBake 2.18.0 reports
`Siggen from metadata (OE-Core?) is too old, please update it (no version found)`
and exits nonzero. Use the explicit two-file comparison above; reinstalling
BitBake or deleting caches does not add the missing lookup policy.

## What incremental execution does not promise

* A parse cache avoids reparsing unchanged metadata; stamps avoid reexecuting
  current tasks. Neither is an archive of compiled output.
* Deleting an output but retaining stamps does not necessarily rebuild it.
  Use `bitbake -C unpack signature-demo` to regenerate from the local input.
* `-f -c measure` forces one task; `-C measure` invalidates it and requests the
  default graph. Forced runs taint hashes, which explains the persistent
  warning introduced in [Chapter 11](ch11.md#why-the-forced-run-warning-persists).
  Removing a taint marker is not the same as regenerating an output.
* Our excluded location variables (`TOPDIR`, `TMPDIR`, `FILE`) are a limited
  tutorial policy, not a license to ignore arbitrary environment or paths.
* BitBake supplies signatures, a setscene scheduling mechanism, and hash
  equivalence infrastructure. OE-Core supplies its `sstate` classes, archive
  layout, restoration tasks and policy. No such cache is configured here;
  “No setscene tasks” is expected. Hash equivalence can identify equal task
  outputs across different input hashes only when suitable output hashing
  and policy are implemented; it is not enabled by setting a server alone.

Run `bash tests/check-ch16.sh` from the repository root. It asserts that an
unchanged task is skipped, a metadata change adds exactly one execution,
an excluded log-only change adds none, a source change adds one, and an
actual signature diff identifies the changed variable.
