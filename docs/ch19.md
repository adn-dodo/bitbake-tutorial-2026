Multiconfig lets one BitBake invocation schedule tasks from several distinct
configuration datastores. This chapter extends Chapter 18 with a `tools`
configuration producing a text artifact and an `image` configuration consuming
it. These names describe roles, not OE machines. The "image" is a text file,
not a bootable filesystem.

Use BitBake 2.18 on `PATH`. From the repository root:

```sh
cd ch19/build
bitbake mc:image:mc-image
cat tmp-tools/deploy/tutorial/tool.txt
cat tmp-image/work/mc-image-1.0-r0/image.txt
```

Expected files, respectively:

```text
tool built in tools
```

```text
image built in image
tool built in tools
```

You requested only the consumer. BitBake also built its producer in another
configuration. Both tasks are `nostamp`, keeping the exercise repeatable; this
is not a model of production incremental artifact management.

Both role-specific recipes set `EXCLUDE_FROM_WORLD = "1"`: they must be
requested through the documented `mc:` target or dependency, not scheduled
in every configuration by `bitbake world`. They remain explicit targets, so
an incorrect direct invocation still produces the useful role diagnostic.

## Configuration discovery and isolation

`build/local.conf` sets `BBMULTICONFIG = "tools image"` and explicitly adds
`include conf/multiconfig/${BB_CURRENT_MC}.conf`. BitBake creates each datastore
with `BB_CURRENT_MC` set; our include finds its configuration through `BBPATH`.
Standalone BitBake does not add this include for you (OE supplies it in its
configuration). Here the files are in `build/conf/multiconfig`. For the default
configuration, the empty-name include is absent and harmless. Because
`include` tolerates missing files, inspect the resulting variables when adding
a new named configuration. The default configuration remains available without
the `mc:` prefix:

```sh
bitbake event-demo
bitbake -e mc:tools:mc-tool | grep -E '^(BB_CURRENT_MC|TMPDIR|CH19_ROLE)='
bitbake -e mc:image:mc-image | grep -E '^(BB_CURRENT_MC|TMPDIR|CH19_ROLE)='
```

`BB_CURRENT_MC` is `tools` or `image`; each file assigns a different role and
`TMPDIR`: `tmp-tools` versus `tmp-image`. The default still uses `tmp`.
Because this tutorial derives `WORKDIR`, `STAMP`, `CACHE`, and `DEPLOY_DIR` from
`TMPDIR`, those paths are separated too. Shared source metadata does not imply
shared task output directories. Distinct names alone do not make arbitrary
output paths safe: inspect variables before running tasks.

In OE, multiconfig commonly selects different `MACHINE`, distribution, or
toolchain settings. None of those policies, nor an OE sysroot or sstate
integration, is supplied by this standalone example.

## The cross-configuration edge

The consumer declares:

```bitbake
CH19_MCDEPENDS ?= "mc:image:tools:mc-tool:do_build"
do_build[mcdepends] = "${CH19_MCDEPENDS}"
```

The fields are `mc:<source configuration>:<destination configuration>:<recipe>:<task>`.
Here the task in `image` waits for `mc-tool:do_build` in `tools`. An empty
source field denotes the default configuration when constructing such an
edge. Ordinary `[depends]` addresses recipe tasks in the same configuration;
it is not the cross-configuration mechanism.

```sh
bitbake -g mc:image:mc-image
grep 'mc:.*do_build.* -> ' task-depends.dot
```

The relevant edge is:

```text
"mc:image:mc-image.do_build" -> "mc:tools:mc-tool.do_build"
```

Arrows point to prerequisites. `mcdepends` supplies ordering; it does not copy
files, construct a sysroot, or discover an artifact path. The producer writes
`tmp-tools/deploy/tutorial/tool.txt`; the consumer explicitly reads the
`CH19_TOOL_ARTIFACT` path and validates its contents. This is a local artifact
contract. If you relocate the tools `TMPDIR`, update that contract as well.

To prove this is not merely reusing an old file:

```sh
rm -f tmp-tools/deploy/tutorial/tool.txt
bitbake mc:image:mc-image
cat tmp-image/work/mc-image-1.0-r0/image.txt
```

Only the named exercise artifact is removed. No broad cache cleanup is needed.
Scheduling both targets on a command line without a dependency would not
establish the required ordering.

## Diagnose an invalid dependency and recover

Use a post-read configuration rather than editing the recipe:

```sh
printf 'CH19_MCDEPENDS = "mc:image:tools:ch19-missing-tool:do_build"\n' > ch19-missing.conf
bitbake -R "$PWD/ch19-missing.conf" mc:image:mc-image
# Expected nonzero exit: Nothing PROVIDES ... ch19-missing-tool
rm ch19-missing.conf
bitbake mc:image:mc-image
```

A configured multiconfig does not guarantee that the requested recipe exists.
For other failures, distinguish configuration discovery errors, missing
providers, and a task's missing-file diagnostic. The recipe also rejects
`bitbake mc-image` with an instruction to use `mc:image:mc-image`; that target's
contract specifically requires the image configuration.

Run `bash tests/check-ch19.sh` from the repository root. It removes only the
producer's exercise artifact, builds the consumer, verifies exact contents
and both `TMPDIR` values, checks the cross-config graph edge, then checks the
missing-provider failure and recovery. This chapter covers explicit local
multiconfig dependencies, not every multiconfig caching or deployment policy.
