This snapshot extends Chapter 19. Five small experiments separate decisions
that are easy to confuse: when a class is selected, how a recipe is extended,
which recipe files are visible, when an optional layer's appends become
active, and which layer's competing recipe wins. They use standalone BitBake
2.18; none requires OpenEmbedded.

From the repository root, enter `ch20/build` with BitBake on `PATH`.

## Immediate versus deferred inheritance

Compare these two recipes:

```bitbake
# select-immediate_1.0.bb
CH20_CLASS = "tutorial-select-early"
inherit ${CH20_CLASS}
CH20_CLASS = "tutorial-select-late"
```

```bitbake
# select-deferred_1.0.bb
CH20_CLASS = "tutorial-select-early"
inherit_defer ${CH20_CLASS}
CH20_CLASS = "tutorial-select-late"
```

Both class files inherit `tutorial-selection-output`, which supplies a
`do_build` task writing `CH20_SELECTED` to `WORKDIR/selection.txt`. The early
class sets that variable to `early`; the late class sets it to `late`.

```sh
bitbake select-immediate select-deferred
cat tmp/work/select-immediate-1.0-r0/selection.txt
# early
cat tmp/work/select-deferred-1.0-r0/selection.txt
# late
bitbake -e select-immediate | grep -E '^(CH20_CLASS|CH20_SELECTED)='
bitbake -e select-deferred | grep -E '^(CH20_CLASS|CH20_SELECTED)='
```

`inherit` expands its class expression when that statement is parsed.
Changing `CH20_CLASS` afterwards does not undo inheritance: the immediate
recipe still uses the early class, although its final `CH20_CLASS` says
`tutorial-select-late`. `inherit_defer` defers the inheritance decision until
recipe finalization, so it sees the later assignment. This is metadata parse
timing, not a task running "late". Deferred inheritance happens before
anonymous Python finalization; do not assume a variable assigned only by
anonymous Python can select such a class.

Use the immediate form for unconditional, straightforward inheritance. The
deferred form is useful when later metadata must influence conditional class
selection. Both experiments still have just a `do_build` task; changing
inheritance timing does not itself add a task dependency.

## A custom class extension

`variant-demo_1.0.bb` sets `BBCLASSEXTEND = "tutorial-alt"`. BitBake creates a
second recipe datastore, gives it the suffixed `PN`
`variant-demo-tutorial-alt`, and inherits `tutorial-alt.bbclass` there. The
class changes `CH20_VARIANT` to `alternate`; the original remains `original`.

```sh
bitbake variant-demo variant-demo-tutorial-alt
cat tmp/work/variant-demo-1.0-r0/variant.txt
# variant-demo: original
cat tmp/work/variant-demo-tutorial-alt-1.0-r0/variant.txt
# variant-demo-tutorial-alt: alternate
bitbake -g variant-demo variant-demo-tutorial-alt
grep 'variant-demo.*do_build' task-depends.dot
```

The graph has two task nodes, not an automatic edge between them. Each has a
distinct `WORKDIR` because this tutorial's path includes `PN`. Asking for the
base target does not implicitly build the variant.

This is deliberately **not** `BBCLASSEXTEND = "native"`. OE's `native`,
`nativesdk`, and multilib classes implement policy such as toolchain,
dependency, and path transformations. Bare BitBake does not provide those
classes, and our custom extension does not turn code into a host tool or
rewrite a dependency graph. In a real extension, isolation and dependency
mapping remain design work, not something a changed label guarantees.

## Mask a file before it becomes a candidate

The chapter configuration appends this regular expression:

```bitbake
BBMASK += "/recipes-selection/masked-demo/"
```

It matches the recipe's full path. `BBMASK` uses regular expressions, not
shell wildcards, and prevents matching `.bb` or `.bbappend` files from being
parsed. It is not equivalent to selecting a preferred provider or version:
a masked candidate is absent.

```sh
bitbake masked-demo
# Expected nonzero exit: Nothing PROVIDES 'masked-demo'
printf 'BBMASK = ""\n' > ch20-unmask.conf
bitbake -R "$PWD/ch20-unmask.conf" masked-demo
cat tmp/work/masked-demo-1.0-r0/selection.txt
# unmasked
rm ch20-unmask.conf
bitbake masked-demo
# Expected missing-provider failure again
```

The recipe is valid; only discovery changes. The second failure also
demonstrates that an old output file is not evidence a target is currently
available. Unmasking an entire configuration is suitable for this isolated
exercise, not a recommendation to discard a project's intentional masks.

## Optional appends with `BBFILES_DYNAMIC`

The extra `meta-selection` layer is opt-in. Its configuration declares the
collection `selection`, a normal recipe search pattern, and:

```bitbake
BBFILES_DYNAMIC += "two:${LAYERDIR}/dynamic/two/recipes-*/*/*.bbappend"
```

`two` is the collection name from `meta-two/conf/layer.conf`, not a directory
test. If that collection is active, the additional glob contributes an append
for `dynamic-demo`. Without it, the append is not discovered. The dynamic
directory deliberately lies outside this layer's ordinary `BBFILES` pattern.

Layers are discovered before `local.conf`, so adding `BBLAYERS` there would
be too late. Rather than change earlier snapshots' `bblayers.conf`, this
exercise supplies a **pre-read** configuration:

```sh
bitbake -r "$PWD/conf/ch20-layers.conf" dynamic-demo
cat tmp/work/dynamic-demo-1.0-r0/selection.txt
# with-two
```

`ch20-layers.conf` appends `meta-selection` to `BBLAYERS` using an override
operator that survives the ordinary assignment in `bblayers.conf`.
For a permanent project, list the layer directly in `bblayers.conf`.

Now keep `meta-selection` but remove the optional `two` collection for one
invocation:

```sh
cat > ch20-without-two.conf <<'EOF'
require conf/ch20-layers.conf
BBLAYERS:remove = "${TOPDIR}/../meta-two"
EOF
bitbake -r "$PWD/ch20-without-two.conf" dynamic-demo
cat tmp/work/dynamic-demo-1.0-r0/selection.txt
# without-two
rm ch20-without-two.conf
bitbake -r "$PWD/conf/ch20-layers.conf" dynamic-demo
# Restored: selection.txt contains with-two
```

The base recipe always exists in `meta-selection`; its default value is
`without-two`. With the collection present, the append changes it to
`with-two`. No missing-append suppression is needed. The layer depends on
`tutorial`, not `two`, so removing `two` is supported. Its conventional
`BBFILE_PRIORITY_selection` declaration is not what turns the append on:
`BBFILES_DYNAMIC` does that. The next experiment isolates recipe priority.

If `dynamic-demo` is missing, check that you used `-r`, not `-R`, and enabled
the layer. If its output differs, inspect `BBFILE_COLLECTIONS`, `BBFILES`, and
the variable's assignment history with `bitbake -r ... -e dynamic-demo`.
Configuration changes automatically invalidate the relevant parse cache; do
not delete the entire build directory to switch modes.

## Competing recipes: layer priority can beat a newer version

Both layers now offer the same recipe name, `priority-demo`, at different
versions:

| Layer | Collection priority | Recipe version |
| --- | --- | --- |
| `meta-tutorial` | `BBFILE_PRIORITY_tutorial = "5"` | `2.0` |
| `meta-selection` | `BBFILE_PRIORITY_selection = "7"` | `1.0` |

With the ordinary layer list, only the tutorial recipe is available:

```sh
bitbake priority-demo
cat tmp/work/priority-demo-2.0-r0/selection.txt
# tutorial 2.0
bitbake -e priority-demo | grep '^PV='
# PV="2.0"
```

Enable the competing layer using the same pre-read configuration:

```sh
bitbake -r "$PWD/conf/ch20-layers.conf" priority-demo
cat tmp/work/priority-demo-1.0-r0/selection.txt
# selection 1.0
bitbake -r "$PWD/conf/ch20-layers.conf" -e priority-demo | grep '^PV='
# PV="1.0"
```

The higher numeric layer priority wins even though its recipe has a lower
`PV`. Neither recipe sets `DEFAULT_PREFERENCE`, and this example does not set
a preferred version for `priority-demo`. This extends Chapter 17's provider
and version exercises with an actual competing-layer selection: do not assume
the highest visible version always wins.

Only the selected recipe contributes this target's task graph; BitBake does
not build both versions merely because both files are discovered. The output
task is inherited from the same `tutorial-selection-output` class in both
cases, so the observed difference comes from recipe selection rather than a
different implementation of that class.

Keep three mechanisms distinct:

* `BBFILE_PRIORITY` influences competing recipe selection. It does not make
  every variable assignment in a layer globally override other metadata.
* `BBPATH` search order locates classes and included configuration files.
  A higher recipe priority does **not** move a layer ahead in class lookup.
* `BBFILES_DYNAMIC` makes additional files discoverable when a collection
  exists. The earlier dynamic append is enabled by collection membership,
  not by this priority contest.

To restore the original selection, omit the command-scoped layer addition:

```sh
bitbake priority-demo
bitbake -e priority-demo | grep '^PV='
# PV="2.0"
```

Both artifact directories can remain on disk. Consult `-e` and the current
build's output rather than treating the existence of an old version's file
as evidence that it remains selected. No recipe edits or cache deletion are
needed to recover the base configuration.

## Check the decisions, not just the exit code

Run `bash tests/check-ch20.sh` from the repository root. It asserts exact
early/late and base/variant artifacts, separate graph nodes, masked-target
failure and explicit unmasking, competing-layer artifacts and selected `PV`,
then dynamic-append activation, absence, and restoration. All output tasks are
intentionally `nostamp`, so stale artifacts
cannot satisfy the checks by accident.

These are selected advanced mechanisms, not a catalog of every parser,
override, layer-priority or OE extension rule. The important distinction is
which stage makes each decision: file discovery, recipe finalization, or
task scheduling.
