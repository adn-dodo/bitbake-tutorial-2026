## Observe a lifecycle without changing it

`local.conf` globally inherits `tutorial-events.bbclass`. Its `addhandler`
registers a Python callback; the `eventmask` limits calls to six event types.
The handler receives `e` (the event) and `d` (the datastore appropriate to that
event). This is not always a recipe datastore:

| Event | Meaning and safe context |
| --- | --- |
| `bb.event.RecipeParsed` | A recipe has finished parsing; read its `PN` from `d`. |
| `bb.event.BuildStarted` | A build operation is starting; do not assume recipe variables exist. |
| `bb.build.TaskStarted` | A task starts; use the event's `pn` and `taskname`. |
| `bb.build.TaskSucceeded` / `TaskFailed` | The task completed successfully / failed. |
| `bb.event.BuildCompleted` | The build operation ended, not necessarily successfully. |

The observer prints information only. Do not use it to implement dependencies,
mutate another recipe, or append concurrently to one shared file. Recipe parse
workers and task workers are separate processes. Messages from different
recipes can interleave; a handler is not a global ordering barrier.

```sh
cd ch18/build                         # from the repository root
bitbake -p
bitbake -v event-demo event-peer
cat tmp/work/event-demo-1.0-r0/hook-order.txt
```

Expected artifact:

```text
pre
body
post
```

The build prints `CH18 EVENT BuildStarted`, task events containing the target
and task name, and `CH18 EVENT BuildCompleted`. `RecipeParsed` messages appear
when recipes actually parse, not necessarily on a warm parse-cache hit.
The observer deliberately prints `RecipeParsed` only when `PN` is
`event-demo`, and task events only for `event-demo` and `event-peer`. Do not
expect one printed parse message for every recipe in the snapshot. Task
workers can parse the recipe again, so repeated `RecipeParsed` messages for
`event-demo` do not imply that its build task ran twice.

To observe a new parse without deleting the cache, create a configuration with
a new value and read it after the normal configuration:

```sh
printf 'CH18_PARSE_CHECK = "exercise-one"\n' > ch18-parse.conf
bitbake -R "$PWD/ch18-parse.conf" -p
rm ch18-parse.conf
```

Change `exercise-one` on subsequent attempts. Parsing is distinct from executing
tasks: `-p` does not run `do_build`.

## A graph edge is not a hook

`addtask prepare before do_build` makes `do_prepare` a separately scheduled,
stamped prerequisite. `do_build[prefuncs]` and `[postfuncs]` run ordinary
functions inside `do_build`, in order around its body. They are not separately
scheduled graph nodes, do not acquire independent stamps, and a fatal error
can prevent post-functions from running. Post-functions are not `finally`
blocks.

```sh
bitbake -g event-demo
grep '"event-demo.do_build" ->' task-depends.dot
bitbake event-demo
bitbake event-demo
```

The graph contains the edge
`"event-demo.do_build" -> "event-demo.do_prepare"`: arrows point from a task
to its prerequisite. It has no `event_before` task node. The second build can
reuse the prepare stamp; `do_build[nostamp] = "1"` always reruns the body and
hooks. The pre-hook truncates the trace, so repeated builds still produce
exactly three lines.

Other flags here affect execution rather than graph topology:

* `[dirs]` creates `WORKDIR` and selects it as the working directory.
* `[lockfiles]` uses the same lock path for both recipes' build tasks. They
  cannot execute their locked sections simultaneously, even with
  `BB_NUMBER_THREADS = "2"`. There is no guaranteed winner and no dependency
  edge between the targets. Locking is useful for a genuinely shared resource;
  it is not a substitute for `depends`.
* `[nostamp]` is an explicit teaching choice, not a performance recommendation.

## Read the evidence, then recover

The body calls `bb.note`, `bb.warn`, and `bb.debug(1, ...)`. A warning does not
make this task fail. `-v` shows notes; `-D` enables level-one debug output.
Debug details are also available in the task log.

```sh
bitbake -v -D event-demo
cat tmp/work/event-demo-1.0-r0/temp/log.do_build
cat tmp/work/event-demo-1.0-r0/temp/run.do_build
```

`log.do_build` and `run.do_build` point to the latest log and generated task
script; numbered files preserve individual attempts. Inspect them rather than
trying to execute generated scripts outside BitBake's task environment.

The `fail` task is deliberately disconnected from the default build graph.
It fails only when explicitly requested with `CH18_FAIL = "1"`:

```sh
printf 'CH18_FAIL = "1"\n' > ch18-failure.conf
bitbake -k -R "$PWD/ch18-failure.conf" -c fail event-demo event-peer
# Expected nonzero exit: CH18 intentional failure: set CH18_FAIL back to 0
cat tmp/work/event-demo-1.0-r0/temp/log.do_fail
rm ch18-failure.conf
bitbake -c fail event-demo
# CH18 failure exercise recovered
```

`bb.fatal` aborts the task; the handler observes `TaskFailed`. `-k` keeps
independent work going, so the peer reports `CH18 peer completed`, but the
overall exit status is still failure. Without `-k`, BitBake stops scheduling
new work after failure (already-running work may finish). Recovery does not
require deleting `tmp`: the override was confined to one command, and this
task is `nostamp`.

## Diagnose a missing host environment variable

BitBake filters the launching shell's environment rather than importing every
variable. Two separate operations are involved:

* `BB_ENV_PASSTHROUGH_ADDITIONS` permits named host variables into the metadata
  datastore. Set it in the **launching environment**, not in `local.conf`:
  environment filtering occurs before metadata can configure it.
* `export CH18_HOST_LABEL` in metadata exports an existing datastore variable
  to task processes. It does not, by itself, import that variable from your
  shell. Python tasks can read the imported value with `d.getVar(...)`.

For a harmless, command-scoped inspection:

```sh
CH18_HOST_LABEL=diagnostic \
BB_ENV_PASSTHROUGH_ADDITIONS="${BB_ENV_PASSTHROUGH_ADDITIONS:-} CH18_HOST_LABEL" \
bitbake -e event-demo | grep '^CH18_HOST_LABEL='
# CH18_HOST_LABEL="diagnostic"
```

These assignments affect only this invocation; no recovery edit is needed.
Prefer explicit metadata configuration for reproducible build inputs. If a
task consumes a host-derived value, that input must participate in its
signature; dynamically accessed inputs may need an explicit task `[vardeps]`
declaration. Do not exclude a real input merely to prevent rebuilds. Do not
pass through the whole environment: unrelated machine-specific values cause
unstable signatures, hidden dependencies, and possible credential exposure
in environment dumps or task logs.

Run the automated checks from the repository root:

```sh
bash tests/check-ch18.sh
```

They check the artifact, lifecycle messages, logs, graph, expected nonzero
failure, independent work under `-k`, and recovery. These examples cover useful
public mechanisms, not every BitBake event or scheduler implementation detail.
OE supplies many additional event handlers and task classes; do not copy this
small standalone `base.bbclass` into an OE layer.
