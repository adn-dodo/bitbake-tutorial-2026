Start in `ch12/build`. BitBake provides **fetcher APIs**, not this project's
source-processing task policy. The copied `base.bbclass` does not define
`do_fetch` or `do_unpack`. We implement them in
[tutorial-fetch.bbclass](../ch12/meta-tutorial/classes/tutorial-fetch.bbclass):

```text
do_fetch -> do_unpack -> do_build
```

Both Python tasks construct `bb.fetch2.Fetch(urls, d)`. `download()` obtains
the inputs; `unpack(destination)` handles copying or extracting them.
Failures propagate as task failures rather than producing empty output.

## Local sources first

[local-source](../ch12/meta-tutorial/recipes-advanced/local-source/local-source_1.0.bb)
uses `SRC_URI = "file://message.txt"`.

Here is its complete metadata; the class supplies fetch/unpack while the
recipe supplies the input and the final observation:

```bitbake
SUMMARY = "An offline source fetched through FILESPATH"
SRC_URI = "file://message.txt"
S = "${UNPACKDIR}"

inherit tutorial-fetch

do_build () {
    cat "${S}/message.txt"
}
```

```bash
config=$(mktemp --suffix=.conf)
printf 'BB_NO_NETWORK = "1"\n' > "$config"
bitbake -R "$config" local-source
cat tmp/work/local-source-1.0-r0/sources/message.txt
rm "$config"
```

Expect `Hello from a local source.`. `file://` searches `FILESPATH`; it does
not mean the task's current directory. The existing configuration includes
the recipe's `files/` directory. `do_fetch[file-checksums]` calls BitBake's
`get_checksum_file_list(d)` so local file contents participate in signatures.
Merely mentioning a filename in a shell task would not track its contents.

The paths have separate purposes:

| Variable | Meaning in this tutorial |
|---|---|
| `DL_DIR` | Download cache, `build/tmp/downloads` |
| `WORKDIR` | Per-recipe work area, including logs |
| `UNPACKDIR` | Our explicit extraction destination, `${WORKDIR}/sources` |
| `S` | Recipe's source tree, here `${UNPACKDIR}` |
| `T` | Generated task scripts and logs, `${WORKDIR}/temp` |

Local files can be used in place; do not expect an extra download-cache copy.
`[cleandirs]` on unpack gives a fresh source tree whenever unpack runs.
It does not delete the recipe's task logs.

## A pinned remote archive (opt-in)

Install host `wget`, `tar` and `gzip` for this example.
[remote-source](../ch12/meta-tutorial/recipes-advanced/remote-source/remote-source_1.3.1.bb)
downloads the zlib 1.3.1 release from its upstream fossil archive and verifies
this SHA-256:

```text
9a93b2b7dfdac77ceba5a558a580e74667dd6fede4585b91eefb60f03b72df23
```

```bash
bitbake remote-source
sha256sum tmp/downloads/zlib-1.3.1.tar.gz
test -f tmp/work/remote-source-1.3.1-r0/sources/zlib-1.3.1/zlib.h
cat tmp/work/remote-source-1.3.1-r0/temp/log.do_unpack
```

The task does **not** compile zlib. Its archive is not bundled in this repo;
`EXCLUDE_FROM_WORLD = "1"` keeps `bitbake world` offline. Explicitly requesting
the recipe still builds it. `[network] = "1"` permits networking for fetch;
it does not override `BB_NO_NETWORK`.

The checksum pins content, not just a URL whose contents might change. A
checksum mismatch is an error: investigate the source rather than replacing
the expected value with an arbitrary new one. With multiple archives, use
URL `;name=...` parameters and corresponding `SRC_URI[name.sha256sum]` flags.

After the first successful download:

```bash
config=$(mktemp --suffix=.conf)
printf 'BB_NO_NETWORK = "1"\n' > "$config"
bitbake -R "$config" -f -c fetch remote-source
rm "$config"
```

Forcing fetch proves the local cache suffices; simply rerunning a stamped
build would not prove that. On a fresh cache, offline remote fetching fails.
The offline alternative requiring no cached archive is `local-source`.

## Git, mirrors, and deliberate scope

An equivalent Git recipe uses a URI such as
`git://host/project.git;protocol=https;branch=main` and a full immutable
`SRCREV` commit ID. Git revision selection replaces archive checksumming;
tags can move, and `${AUTOREV}` deliberately queries the moving tip, so neither
is a reproducible offline pin. Git URLs use `git://` to select the Git fetcher
even when the transport is HTTPS. We use the real pinned archive above to
keep the executable example small.

Fetch lookup normally tries an existing local download, `PREMIRRORS`, the
original URI, then `MIRRORS`. These are regex URI rewrite policies, not
task dependencies. `BB_FETCH_PREMIRRORONLY` restricts retrieval to premirrors;
`BB_ALLOWED_NETWORKS` restricts allowed network hosts.
They are useful extensions for a managed download service, not needed for
our checked-in local file. See the versioned
[fetching manual](https://docs.yoctoproject.org/bitbake/2.18/bitbake-user-manual/bitbake-user-manual-fetching.html)
for transport-specific options, submodules and mirror tarballs.

From the repository root:

```bash
bash tests/check-ch12.sh            # no network
bash tests/check-ch12.sh --network  # archive, cached offline fetch, wrong-checksum rejection
```

The second check deliberately supplies an incorrect checksum, requires the
failure diagnostic, and then restores the valid cached download. Its network
access is intentional.
